## 第一步：意图扩展

### 判断标准

用户意图"过于简单"是指以下任一情况：
- 缺少具体布局描述（如只说"做一个监控页面"，没说布局结构）
- 缺少数据细节（如只说"显示一些指标"，没说具体指标和数值）
- 缺少区域划分（如只说"网络管理界面"，没说分几个区域）
- 缺少组件类型说明（如只说"图表"，没说什么类型的图表）
- 整体描述少于3句话

如果用户意图已经足够详细，则直接标准化，无需扩展。

### 扩展原则

1. 根据用户描述的业务场景，推断合理的页面布局模式
2. 补充各区域的功能描述和组件选型
3. 补充高拟真的业务Mock数据
4. 保持扩展内容与用户原始意图一致，不偏离业务方向
5. 从界面完整性、界面丰富度、数据完整性、数据丰富度4个角度考虑扩展
6. **不要自行添加用户未明确提到的壳层区域**（如aside、dialog、drawer等），用户没说就不要加

### 扩展方向

- 界面丰富度：除了用户要求的功能之外，还有哪些常用的相关功能模块？
  - 如：用户要求数据看板页，通常还包含关键指标概览模块、核心趋势分析模块、构成与分布模块等

## 第二步：意图标准化

将扩展后的意图按照以下模板转换为标准化的JSON格式。

### 页面壳层模板（🔴不可改 🔵可选 🟡可改）

**壳层结构是强制约束（CRITICAL）**：
- `root → header + body + footer(可选)` 结构不可改
- `body → aside(可选) + main(必须)` 结构不可改，body 下只能有 aside 和 main，禁止放其他节点
- **rightPanel 必须放在 main 的 children 里，禁止放在 body 下（CRITICAL）**：当页面有右侧面板时，rightPanel 是 main 的子节点，与 mainContent 并列
- footer 必须放在 root 的 children 里，与 header、body 并列，在 body 下方；footer 必须是叶子节点，不能有 children
- main 的子节点根据用户意图自由组织，典型结构为 mainContent + rightPanel(可选)
- 禁止跳过 main 直接在 body 下放置内容节点
- **{{独立区块：...}}包裹标记（CRITICAL）**：必须创建一个父节点包裹标记内的所有内容，该父节点设置 containerType:"Region"，标记内所有内容作为该父节点的children。禁止将包裹内容拆分到多个独立节点

### 节点类型规范

1. **叶子节点**：只有 description 和 style 属性，用纯文本描述该节点的内容
   - header、infoBar、dialog、drawer、aside 等简单模块均为叶子节点，不再展开children，用description描述其内容
    - style 约束见关键规则第1条
    - 如果叶子节点本身是组件（如图表、按钮、输入框等），则没有layout属性
   - 如果叶子节点本身还是区域（如header、aside等），则有layout属性描述其排列方向
2. **非叶子节点**：只有 layout / layoutDescription / children / style 等结构属性，不能有 description
   - root、body、main 等容器节点为非叶子节点，需要展开children
    - style 约束见关键规则第1条，不再使用单独的width属性
   - main 节点是页面核心内容区，必须重点展开，详细描述每个子模块
3. **模板引用节点**：通过 template 字段引用模板，只传数据props
   - 例: {{ template: "统计块", value: "1574", label: "运行中" }}
   - 例: {{ template: "堆叠折线图卡片", title: "计算资源池监控", series: "核心集群>84% | 高频区6%~09% | 闲置区" }}
4. **重复内容容器**：当页面中有重复结构（列表、多个重复卡片等）时使用
   - itemTemplate 描述每项的结构
   - data 数组存放数据，用｜分隔标题与数据，／分隔多组数据

### 关键规则

1. **style属性约束（CRITICAL）**：style只能用中文语义描述（如"固定宽度240px"），禁止写Tailwind className（如"p-4 gap-4 flex-1"等）。只记录用户意图中明确提到的样式，禁止自行创造用户未提及的样式。叶子节点和非叶子节点均可使用style
   - **壳层节点（header/aside/infoBar/dialog/drawer）禁止自行添加宽度样式**：这些节点的宽度由布局系统自动处理，除非用户明确说了"侧边栏宽度240px"等，否则不要在style中写"固定宽度Npx"
2. 叶子节点只有description和style，不能有children；区域型叶子节点有layout，组件型叶子节点没有layout
3. 非叶子节点不能有description，只能有layout/layoutDescription/children/style/itemTemplate/data等结构属性，不再使用单独的width属性
4. header、infoBar、aside、dialog、drawer等简单壳层模块必须是叶子节点，用description描述内容
5. main节点必须重点展开，详细描述子模块的布局、数据和组件
6. **重复结构必须使用 itemTemplate + data（CRITICAL）**：2个及以上结构相同的元素禁止逐个展开，必须用重复内容容器描述。仅当每项布局/结构不同时才可逐个展开。
7. 保留原始意图中的所有数据，不丢失任何信息
8. **叶子节点的description必须清晰说明采用什么组件**：不要只写"显示指标数据"，要写"4个PatGauge仪表盘，分别显示CPU/内存/磁盘/网络使用率"；不要只写"图表区域"，要写"LineChart折线图展示24小时流量趋势"
9. **图表选型约束（CRITICAL）**：选择图表类型时必须严格匹配数据特征：
    - **多分类占比分布**（如：手机33%/平板17%/其他17%）→ **必须用 PieChart**（`option.type: "circle"` 可做环形），PieChart 有内置图例
    - **单值进度/利用率**（如：CPU 75%、容量用了82%）→ 用 CircleProcessChart，CircleProcessChart 无图例，只展示一个数值的进度环
    - **TopN 排行/水平对比** → 用 ProcessChart（水平条形图）
    - **趋势变化** → 用 LineChart
    - **离散类别数值对比** → 用 BarChart
    - 严禁将多分类分布数据塞进 CircleProcessChart
10. **{{}}标注保留（CRITICAL）**：用户意图中用 `{{...}}` 标注的内容是结构/语义约束标记，必须在标准化JSON中完整保留。
    - `{{独立区块}}` → 该节点设置 containerType:"Region"
    - `{{独立区块：...}}` → 创建父节点 containerType:"Region"，包裹内所有内容作为children
    - `{{水平排列}}` → 该节点 layout:"horizontal"
    - `{{垂直排列}}` → 该节点 layout:"vertical"
    - `{{宽度Npx}}` → 该节点 style 中加入 "固定宽度Npx"
    - 禁止省略、改写或丢失任何 `{{}}` 标注
    - 详见 {ANNOTATIONS_RULES}

## 输出格式

**只输出一个完整的standardizedIntent JSON对象，禁止输出任何自然语言、分析、步骤说明。** 重复结构必须使用 itemTemplate + data，禁止逐个展开。
