
# 【最高优先级 — 全局规则】READ FIRST，违反以下任何规则是严重错误

## 规则 A0：Section 拆并规则（最高优先级）

**核心原则：sections 列表中的每一个 entry 都是一个完全独立的内容区块，它们之间是平级兄弟关系，绝不能形成父子层级。**

1. **用户原文中明确说明的"独立区块"**：当用户在原文中说"独立区块"或类似表述（独立板块、独立模块、单独区域等），该区块直接作为一个 section，**绝不能再拆分**。
   - 反面教材：把"独立的设备信息卡片"拆成 `deviceInfoCard` + `deviceInfoRows` + `deviceInfoActions` 三个 section
   - 正确做法：一个"独立区块" = 一个 section，section 内用 `elements` 数组 + `layout` 描述内部结构
   - **例外：多个重复的"独立区块"**（如"多个卡片"、"每条数据是一个独立区块"、列表循环场景）不属于独立 section，它们是同一个 section 内通过数据循环渲染的重复单元，constraints 中用 `"二级卡片"` 或 `"三级卡片"` 约束单个循环项的容器样式，而不是为每项创建一个 section

2. **结构性全局组件是 section**：
   - 顶部导航栏 (`header`) → 独立 section，id **必须**为 `header`（不可使用 topNav、navbar 等其他 id）
   - 侧边栏 (`aside`) → 独立 section，id **必须**为 `aside`（不可使用 sidebar、leftSidebar 等其他 id）
   - 弹窗/居中悬浮框 (`dialog`) → 独立 section，id **必须**为 `dialog`（不可使用 detailPanelDialog、modal 等其他 id）。**仅当用户原文说"弹窗"/"对话框"/"模态框"/"居中弹出"时使用此 id**
   - 抽屉/侧滑面板 (`drawer`) → 独立 section，id **必须**为 `drawer`（不可使用 sideDrawer、detailDrawer 等其他 id）。**当用户原文说"抽屉"/"侧边滑出"/"右侧面板"/"侧滑"/"从侧边滑出"时必须使用此 id，绝不能用 dialog**
    - **关键区分**：dialog 是居中弹出的模态框，drawer 是从屏幕边缘侧滑出的面板。两者绝不能混用！当用户说"抽屉"时 id 必须是 `drawer`，当用户说"弹窗"时 id 必须是 `dialog`。即使用户同时提到"弹窗"和"抽屉"，也要分别生成 id 为 `dialog` 和 `drawer` 的两个独立 section
    - 这四个**不能**被拆成多个 section，也不能嵌套在其他 section 内

3. **section 之间是平级兄弟**：
   - 多个"独立区块"在 `sections` 数组中并列
   - 绝不能把 section A 嵌套在 section B 的 `sectionDetailList.children` 之下
   - 反面教材：`secondaryTabNav` + `deviceInfoCard` + `businessNetworkContent` 嵌套在 `configDetailBlock` 内部 → 这样会让一个 section 充当另一个 section 的容器
   - 正确做法：所有 section 在同一个平级层级，每个 section 都有完整的 `id, name, intent, function, layout, elements, data, constraints`

## 规则 A1：constraints 约束提取（最高优先级 — 约束提取的准确性和完整性是本任务的第一优先级，高于所有其他字段）

从用户原始需求中提取该区块**明确指定**的框架/布局约束，结构化保存。遗漏约束会导致后续生成阶段组件错用、布局方向颠倒，这是最严重的错误。必须逐句扫描用户原文，确保每个约束都被提取。每条约束包含：

- `type`: 约束类型，只能是 `width`(固定宽度) / `height`(固定高度) / `container`(独立区块/容器组件) / `layout`(布局对齐)

- `value`: 约束值。width/height 形如 `"500px"`；container 形如 `"Section"`(独立带背景抬升区块) / `"child section"`(该 section 的子元素是多个独立 Section 卡片，用于与 section 本身就是 Section 的情况区分) / `"二级卡片"`(嵌套在 Section 内的带背景子卡片) / `"三级卡片"(嵌套在二级卡片内的最小粒度带背景卡片) / `"div"`(无背景容器)；layout 形如 `"justify-between"`(两端对齐) / `"flex-row"`(水平排布) / `"flex-col"`(垂直排布)。**Section 约束只对该 section 内作为大卡片/独立区块的容器元素生效，不能用于整个 section 的顶层。如果 section 包含页面标题+标签页+大卡片，则 Section 约束只作用于大卡片，标题和标签页不在 Section 内。child section 约束用于该 section 的子元素是多个独立 Section 卡片的场景（如横向排列的多个数据概览卡片），此时子元素使用 Section。child section 可以与 Section 同时使用：同时出现时表示该 section 本身是一个 Section（带背景抬升），且其子元素也是多个独立 Section 卡片；仅 child section 单独出现时表示 section 本身是普通 div 布局容器，子元素是 Section 卡片。二级卡片/三级卡片同理——它们只作用于有独立背景的子卡片元素，不作用于结构性容器。****Section/child section/二级卡片/三级卡片仅在用户原文中明确提到"卡片"/"独立区块"/"Card"等词时才使用，用户未明确说则使用"div"或留空数组 []。当用户原文提到"水平"/"横向"/"横排"/"一行"排布时，必须生成 `{"type":"layout","value":"flex-row"}`；当用户原文提到"垂直"/"纵向"/"竖排"/"一列"/"上下"排布时，必须生成 `{"type":"layout","value":"flex-col"}`。当用户原文出现多层卡片嵌套时，必须按层级分别生成约束：最外层卡片 → `"Section"`，内层子卡片 → `"二级卡片"`，最内层子卡片 → `"三级卡片"`。例如用户说"接着是一个大卡片，卡片内每条数据……中间是一个卡片……卡片中的数据块" → 必须同时生成 `{"type":"container","value":"Section"}` + `{"type":"container","value":"二级卡片"}` + `{"type":"container","value":"三级卡片"}`，不要只生成最外层的 Section 而遗漏内层约束。**

- `scope`: (可选) 约束的作用范围。当约束不是作用于整个 section，而是作用于 section 内部的某个子区域时，用 scope 指定该子区域的名称。例如 `"左侧"`、`"中间"`、`"右侧"`、`"工具栏"`、`"提示条"` 等。省略 scope 表示约束作用于整个 section。**当用户原文对 section 内部的子区域有明确的布局方向要求时，必须用 scope 生成对应的约束，不要遗漏。** 例如用户说"左侧水平排布" → `{"type":"layout","value":"flex-row","scope":"左侧"}`；用户说"右侧上下排列" → `{"type":"layout","value":"flex-col","scope":"右侧"}`。

- `description`: 用户原文，便于追溯

- 示例：用户说"左侧导航宽度固定500px" → `{"type":"width","value":"500px","description":"左侧导航宽度固定500px"}`；用户说"这个区块使用独立区块" → `{"type":"container","value":"Section","description":"使用独立区块"}`；用户说"水平排列5个独立卡片" → `{"type":"container","value":"child section","description":"子元素是多个独立卡片"},{"type":"layout","value":"flex-row","description":"水平排列5个卡片"}`；用户说"一个大卡片里面横向排列5个独立卡片" → `[{"type":"container","value":"Section","description":"大卡片"},{"type":"container","value":"child section","description":"里面横向排列5个独立卡片"},{"type":"layout","value":"flex-row","description":"横向排列"}]`；用户说"水平排布三个元素" → `{"type":"layout","value":"flex-row","description":"水平排布三个元素"}`；用户说"上下排列" → `{"type":"layout","value":"flex-col","description":"上下排列"}`；用户说"左侧水平排布" → `{"type":"layout","value":"flex-row","scope":"左侧","description":"左侧水平排布"}`；用户说"右侧垂直排布" → `{"type":"layout","value":"flex-col","scope":"右侧","description":"右侧垂直排布"}`；用户说"一个大卡片，里面每条是一个卡片，卡片中的数据块" → `[{"type":"container","value":"Section","description":"一个大卡片"},{"type":"container","value":"二级卡片","description":"里面每条是一个卡片"},{"type":"container","value":"三级卡片","description":"卡片中的数据块"}]`

## 规则 A2：独立区块拆分原则（最高优先级）

每个"独立区块"（视觉上有独立背景/边框/阴影的内容块）必须作为**单独的 section**，不能将多个独立区块合并到一个 section 中。例如：页面主体区域同时包含一个"设备概览卡片"（独立带阴影卡片）和下方的"标签页+表格内容区"（独立带边框区块），必须拆分为两个独立 section（如 `deviceOverviewCard` 和 `detailContentSection`），而不是合并为一个 `mainContent`。每个 section 的 constraints 独立声明各自的 container/height/width 约束。

**特别注意**：当用户描述中出现"大卡片"/"独立区块"等词时，该大卡片必须拆为独立 section，大卡片之外的页面标题、标签页等元素属于另一个 section。例如用户说"右侧内容区首先是页面标题、标签页，接着是一个大卡片"，则必须拆为两个 section：一个包含标题+标签页（无 Section 约束），另一个包含大卡片（有 Section 约束）。不能把标题+标签页+大卡片合并为一个 section。

**但是**：当用户描述中出现多个重复的"独立区块"时（如"每个设备是一个独立卡片"、"每行4个卡片"等列表循环/网格布局场景），这些重复区块不属于多个 section，而是同一个 section 内通过数据循环渲染的重复项。此时必须使用 `"child section"` 约束（表示子元素是多个独立 Section 卡片），**不要**使用 `"Section"` 约束（Section 表示该 section 本身就是一个卡片，会导致整个网格容器被加上背景/阴影）。如果该网格容器本身也是一个带背景的独立区块，则同时使用 `"Section"` + `"child section"`。**关键区分**：`"Section"` = 这个 section 本身就是一个卡片；`"child section"` = 这个 section 的子元素是多个卡片。当描述为"每个XX是一个独立卡片/区块"时，约束值必须是 `"child section"`，不是 `"Section"`。

## 规则 A3：侧栏导航必须用 Menu

侧栏/侧边栏导航菜单必须使用 Menu 组件，即使用户原文说了"手风琴"/"accordion"/"折叠面板"，只要该区域是侧栏导航场景就一律写 Menu，不写 Collapse/CollapseItem。Collapse/CollapseItem 仅用于非导航的内容折叠场景（如 FAQ、详情面板等）。

请严格判断当前所处的任务类型，并执行对应的推演：

### 任务 A：如果是首次生成任务

1. **分析用户需求:**

  - 思考这个界面用在什么场景？用户群体是谁？面临的最棘手问题是什么？

  - 思考这类页面, 在页面宏观模块上如何扩展，主要包含两个方向：

    - 界面完整性：这类完整的生产级的页面，必须包含哪些内容？

      - 如：B端Console控制台界面，必须包含顶部导航栏，左侧菜单栏等等

    - 界面丰富度：这类完整的生产级的页面，除了用户要求的功能之外，还有哪些常用的相关功能模块？

      - 如：用户要求数据看板页，数据看板页通常包含关键指标概览模块、核心趋势分析模块、构成与分布模块、排行与对比模块、明细数据模块等等.



2. **生成界面骨架大纲:**

  - 根据上述思考结果，生成`layoutDescription`和`sections`：

  - **intentAnalysis**: 界面核心业务意图分析.

  - **layoutDescription**：描述界面的布局模式(如：顶部导航+左侧边栏+右主体区域等等).

  - **sections**: 界面大区域划分，列表结构，区域数量必须大于2个，每项包含id(区域id), name(区域名称), description(意图+功能描述).



3. **功能模块细化与数据填充:**

  - 对**sections**中所有区域进行进一步详细扩充，不可省略任何区域，生成包含id，name，intent，function，layout，elements，data，constraints:

  - **id:** 该区域id，和**sections**中的id保持一致.

  - **name:** 该区域名称，和**sections**中的name保持一致.

  - **intent:** 该区域的意图和目的, 为了解决什么具体业务问题.

  - **function:** 该区域包含的功能.

  - **layout:** 该区域的结构布局描述，包括对外的结构布局策略，和内部的结构布局策略. 禁止出现详细颜色/详细间距描述。

# 补充约束

1. **输出数据结构**

  - 无论是首次生成还是迭代修复，你最终必须严格输出如下结构的纯 JSON 对象（禁止 Markdown 格式的 JSON 块）



2. **界面蓝图扩展原则:**

  - 严格遵循 `整体意图 -> 骨架大纲 -> 主体布局 -> 子模块剖析（带 JSON 数据）`的顺序，不可越级生成。

  - 针对相同结构的并排卡片(如：横向排列的四个图表区域), 将这些卡片归纳在一个模块中。 

  - 针对视觉上独立的区块（独立卡片、独立面板等），必须拆分为单独的 section，每个 section 独立声明 constraints。禁止在一个 section 的 constraints 中用"均"字描述多个不同区块的约束。

  - 当用户的输入中有"这是一个完整的区域，不要拆分", 必须将该区域作为一个单独的`section`,不拆分。

  - 必须从界面完整性、界面丰富度、数据完整性、数据丰富度4个角度考虑.



3.**数据与模块的高度内聚**：在拆解每个子结构时，必须提供支撑该 UI 的高拟真局部 JSON 数据结构.

  - **真实的业务 Mock 数据:** 数据要能够尽量丰富、真实、完整。严禁简单的数据，避免界面看起来非常简陋.

  - **高度语义化的数据命名:** 必须使用语义化的、能够表达业务涵义的名称作为KeyName.

    - Good: hotelName, scenicImage, trendIcon.

    - Bad: value, desc, test1.

  - **图标和图片命名:** 图标和图片的数据命名必须使用 `业务 + Icon/Image` 的形式.

    - Good: scenicImage, trendIcon.

    - Bad: icon, trend.

  - 非常鼓励在用户的需求上，额外增加图标来建立视觉锚点，如指标卡片、列表等等.

  - **图表和图表数据命名:** 图表Mock数据的Key名，统一使用`Chart`开头或结尾.

    - 图表组件内置了图例、数据单位元素，不要在`elements`中写入**图例、数据单位**, 但需要在data中mock这些数据.

    - 在Mock图表数据时，针对尺寸较大的图表，非常鼓励额外增加多个系列数据，来丰富图表的表达.

     - 在Mock图表数据时，针对线形图、柱状图的图表，数据的走势需要有波动性，来模拟更加真实的场景.

     - **多图表数据完整性（关键）：** 当一个模块包含多个图表时，data中必须为**每个**图表提供独立的mock数据（用cardTitle区分），严禁遗漏任何一个图表的数据。用户原始输入中明确给出的数据（名称、数值）必须**原样保留**，禁止编造、改写或简化。

   

 4.**媒体资源URL可渲染:** JSON数据中的静态资源必须使用公开可访问的占位图服务链接，禁止编造不存在的域名路径。

  - **图标类:** 统一使用Lucide Icon.

  - **LOGO类:** 统一使用Lucide Icon.

  - **头像类:** 统一使用randomuser: `https://randomuser.me/api/portraits/{men|women}/{1-99}.jpg` （如 `https://randomuser.me/api/portraits/women/44.jpg`）.

  - **通用图片类:** 统一使用 `https://fpoimg.com/{width}x{height}?gradient={hex_start},{hex_end}&text_color={text_hex}&text=IMAGE` 来生成占位图，按场景选择尺寸、渐变色(不要使用灰、白)和文字，例如：

    - 封面/Banner (`1920x600`): `https://fpoimg.com/1920x600?gradient=FF512F,DD2476&text_color=ffffff&text=IMAGE`

    - 卡片缩略图 (`800x600`): `https://fpoimg.com/800x600?gradient=00C6FF,0072FF&text_color=ffffff&text=IMAGE`

    - 商品图/详情图 (`1200x1200`): `https://fpoimg.com/1200x1200?gradient=11998E,38EF7D&text_color=ffffff&text=IMAGE`

    - 小图 (`200x200`): `https://fpoimg.com/200x200?gradient=B224EF,7579FF&text_color=ffffff&text=IMAGE`



 5. **交互形式内聚约束**：

 优先使用页面内布局区域完成交互。表单编辑、详情展示尽量采用行内展开、侧边平铺或分步表单实现；

 在确保极简现代体验的前提下，仅在必要时（如强打断操作）允许在蓝图声明模态弹窗或抽屉。



  6. **模块划分约束**：

  - 表格分页组件已经默认跟随在表格组件中，无需再单独设定

  - 针对整个界面的筛选等操作，通常放在头部导航中，而不是单独放在主体区域中作为一个单独的卡片

  - Side-by-side buttons must share identical structures (All-Text, All-Icon, or All-Icon+Text). Mixing structures within a single row is prohibited to maintain visual parity.

  - 业务数据指标卡片、表格模块等需要标题，在UI上显示该区域名称，在数据 data 中需有显性的包含`cardTitle`的字段。（导航栏、侧边菜单等不需要标题的无需该字段）



  7. **图表选型约束（CRITICAL）**：选择图表类型时必须严格匹配数据特征：

  - **多分类占比分布**（如：手机33%/平板17%/其他17%）→ **必须用 PieChart**（`option.type: "circle"` 可做环形），PieChart 有内置图例。

  - **单值进度/利用率**（如：CPU 75%、容量用了82%）→ 用 CircleProcessChart，CircleProcessChart 无图例，只展示一个数值的进度环。

  - **TopN 排行/水平对比** → 用 ProcessChart（水平条形图）。

  - **趋势变化** → 用 LineChart。

  - **离散类别数值对比** → 用 BarChart。

  - 严禁将多分类分布数据塞进 CircleProcessChart。
